## Expert weight decision (v1 contradicted itself; fixed)

24·128·3·2304·1152 = 24.46e9 expert params → **8-bit resident experts are infeasible: 22.78 GiB before scales or any other allocation. Destination representation (DECIDED, by converter inspection): this repo executes no GGUF block format — `tools/convert` writes only its groupwise-int/BF16/FP formats and no Turing kernel exists for Q4_K/Q5_0/Q8_0 layouts — so every matrix is requantized at convert time from decoded source values into repo formats:** expert gate_up → `q4_g64_fp16`, expert down → `q5_g64_fp16`, attention matrices (source Q8_0) → `q8_g32_fp16`, embedding → `q4_g64_fp16`, lm_head → `q6_g64_fp16`; F32 vectors, conv taps, norms and controllers stay FP. Source of truth is the tensor inventory, not the filename (actual file: gate_up Q4_K + down half Q5_0/half Q8_0 = 15.19 GiB experts; 16.55 GiB total). Expected port weight footprint ≈ 15.1–15.6 GiB — established by **measurement** at the first integrated checkpoint. Requantization error is the numerical risk (gate_up passes through two 4-bit stages); the PPL gate on the pinned corpus qualifies it. Size knobs held in reserve, chosen by evidence: down q5→q4 (≈ −1.6 GiB) or gate_up q4→q5 (≈ +2.0 GiB). Convert-time path: GGUF block → decode to FP exactly → `grouped_absmax` to target format; **measure** per-tensor decoded-value error against the decoded source — the group layouts differ, so error is not assumed ~0. Parity attribution: port-vs-server differences mix implementation error and requantization error; attribute any divergence, never average it away.

## Oracles

Primary: greedy logit parity vs ninfer-all :8191 with **matched effective weights** (the port's packed tensors). Per-Op: FP32 CPU references, each qualifying its Op independently — greedy agreement alone cannot qualify clipping, routing, sinks, or residual mixing. Tiebreaker: llama.cpp #32694. Behavior: K2-program markers qualitative-first; the CoT-termination overrun count is the one numeric probe.

## Risks (re-ranked)

1. **Routed-expert execution on 128 experts without FP8** — substantial, not proven secondary: fixed-shape Q4 table plus per-top-k gather/scatter strategy is its own engineering line.
2. **No int8 attention path shapes everything KV-side** — v1 accepts the BF16/FP16 KV cost; int8 KV is deferred, not defaulted.
3. Fused relative-bias attention (bias+sink+gate, split-K) remains the core new-kernel work; basalt's math + this repo's split-K idiom (`kSlidingWindowMaxSplits`), not basalt's cluster structure.
4. 48 state-sets per token: state layout, not FLOPs, decides decode speed — design at M0, before M3.

## Turing quantization program (deferred track, explicitly out of v1)

What the K2 program actually measured: IQ4_XS+imatrix Pareto-dominated Q4_K_M (speed, size, behavior drift); imatrix repairs ~1/3 of the RTN gap; Q8_0 free at 8.5 bpw; refusal behavior quantization-invariant; the only measurable 4-bit cost was thinking-termination overruns. ConvRot / GTPQ / PRISM-Q were **citations only, never implemented** (Claude's audit flagged GTPQ as likely GPTAQ, arXiv:2504.02692) and died with the K2 scope → [[Concepts/ML-theory/Abliteration-Quantization-Transferables]].

Hardware-native quantization (INT8 tensor cores; INT4 via Turing DP4A — the 2080 Ti has both) is a real opportunity but belongs **after M4**: it reworks the same linear dispatch and dequant machinery this port must first stand on, and Inkling — MoE, experts being the whole resident budget — is the best second client for it (expert quantization quality is where calibrated INT4/INT8 paths pay most). Plan: its own roadmap once M4 records the ordinary-decoding baseline; not coupled into port v1.

First planned experiment (2026-11-24, tier-floor probe): rebuild with a 4/8-only recipe — experts all Q4 (down Q5→Q4, −1.07 GiB), attention Q8 (unchanged, behavior-free), lm_head Q4 or Q8 (−0.13 GiB / +0.12 GiB), embedding Q4 — target ≈13.2 GiB, two kernel families, DP4A/IMMA-native widths. Gate = pinned parity corpus + behavior probes (K2 drift evidence predicts pass; a Q5/Q6 behavioral need must show there, not be assumed here). Tier surgery after this is calibration territory (imatrix ≈ ⅓ of RTN gap, measured), not more bit-width dialing.

Format verdict (2026-11-24): no new container/format family is needed for Turing. Decode is bandwidth-bound, so the existing groupwise 4/8-bit formats + fused-dequant A16 kernels are the right storage; "Turing-specialized" lands in (i) recipe tier choice, (ii) an int8 tensor-core-major layout tag with activation-friendly scale order (and ConvRot-style rotation baked at convert time) if/when W8A8 is entered, and (iii) an A8 activation policy beside A16Only — entered only after M4 shows compute-bound work worth serving. W4A8 is excluded on our own measurement (memory not time, ~2× error vs int8). PRISM-Q-style trellis int8 is the theoretical optimum but stays an experiment: sm_75 JIT decode unverified, 250× fallback risk. Kernel landmine on record: SM75 int8 GEMM shape holes (M=97..127 fail via the cublas int8 path in the image stack) — batch-shape handling is a named M3/W8A8 risk.
